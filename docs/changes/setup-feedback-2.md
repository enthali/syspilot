## Intent And Outcome

**Status:** approved<br>
**Approval evidence:** On 2026-11-06 the User agreed the described intent was clear and requested starting the Change in autonomous mode, after reviewing the added Setup findings. ### Goal

A User can start pristine Setup in an ordinary Copilot session. When that session lacks the Jarvis capabilities needed to continue, Setup obtains an Admin Actor and transfers the work to an Admin session; Setup creates Actors through Jarvis rather than writing their Actor files directly. The resulting installation has usable Actor references and project-appropriate documentation, and Setup only reports completion after its mandatory gates pass.

### Value

The first practical Setup test initially stopped because the initiating session did not expose the Jarvis actor-listing, chat-session-listing, or messaging tools required by the Contract. The later test state also recorded incomplete verification while claiming a verified baseline and handoff, alongside broken generated references. A defined bootstrap lets Setup progress without assuming an ordinary session has an Actor's tool bindings; reliable gates and usable generated artifacts make completion meaningful. Jarvis remains responsible for creating its own Actors.

### Scope

- Install role cards and Contract processes under `docs/<Project name> Actors/` and `docs/<Project name> Contracts/`, using the same User-confirmed project name as the documentation scaffold instead of hard-coded Syspilot branding. Generate all dependent registries, navigation, Actor summaries/context references, installed Contract references and handoff paths consistently. Reconcile project-specific substitutions with seeded-copy identity verification. Preserve the Syspilot source/example locations; this extension governs fresh target installation, not migration of existing projects or renaming the current test evidence.
- If Jarvis Core is absent in the active VS Code instance and profile, explain its purpose for Actor communication and ask whether to install `enthali.jarvis-core` from the Marketplace there. Install only after consent; refusal stops Syspilot Setup with a recorded blocker. Verify the active instance/profile rather than relying on an unqualified `code` command that may inspect another installation. Report installation failures explicitly and offer a manual path. Recheck the required version and actual session tools after installation; request reload only when necessary, not as an unconditional step.
- Check the capabilities needed to execute Setup before the first step that uses them. If the initiating session lacks the required tools, arrange continuation by the Admin Actor rather than pretending the checks or message delivery succeeded.
- Create Actors using Jarvis's supported creation function, not by directly writing their Actor files. Preserve existing Actors and make collisions and failed creation explicit.
- Place a Setup request for Admin in `.jarvis/messages/queue.json` and include Admin in `.jarvis/messages/autodelivery.json`, retaining entries observed before each write. For a newly created Admin, Jarvis queues the request through `initialMessage`; for an existing Admin, Setup may directly append with the User's consent in that step. The short direct read-modify-write of `autodelivery.json` applies to both cases. The User accepted that these direct writes can lose an intervening concurrent update, which readback cannot reliably detect; preservation is not guaranteed against that race. The Setup Contract states these limits and verifies continuation. If Actor creation, queueing, automatic delivery, or continuation is unavailable or fails, report it and give the User an actionable manual path and prompt.
- Compose the Setup request in the language the User used with the initiating session; use English when that language is ambiguous. The manual prompt follows the same rule.
- Reconcile the executor, responsibility transfer, before-and-after checks, existing-Admin handling, Actor contexts, and session-discovery requirements with an Admin that may be created and started during Setup.
- Address the observed premature verification and handoff: open or failed mandatory gates must remain visible and prevent a verified baseline and successful handoff, including when Actor discovery is pending or the documentation build has warnings.
- Address generated Actor-context references so they resolve to the installed role cards and Contract registry from the actual Actor context location.
- Address the test's generated documentation configuration and navigation: project-specific defaults and references must be appropriate to the target, and absent source-project pages or assets must not be required by a pristine target. Preserve existing project documentation according to the Setup Contract. Assess the observed automatic ontology-reference generator against the existing product decision before specifying any such generation.
- Update the relevant Setup specification, Requirements, verification, examples where applicable, and user-facing documentation. The Architect identifies the affected artifacts.
- This Change addresses the observed Setup bootstrap, Actor creation, verification, and generated-artifact behavior; an isolated-VS-Code or Windows Sandbox test harness and its release policy are not specified by this Change.

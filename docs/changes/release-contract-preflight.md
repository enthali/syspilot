## Intent And Outcome

**Status:** approved<br>
**Approval evidence:** On 2026-11-09 the User agreed to the discussed release simplifications and requested adjusting the Contract, then explicitly approved Contract release in autonomous mode.

### Goal

The Release Contract clearly assigns release artifacts and supports Syspilot's source-based release without a mandatory duplicate pre-tag Linux workflow run for every version.

### Value

A release promotes a verified source state to `main` and a version tag, publishes documentation and creates a GitHub Release. Explicit ownership and bounded preflight evidence avoid unnecessary ceremony without implying that local tests prove Linux execution or publication.

### Scope

- Keep Release responsible for the Change inventory, version, preflight evidence, release notes, publication and closure. Technical Writer owns user-facing documentation; Release ensures release completeness through those owners. Reconcile conflicting role, specification, Contract and example statements.
- Keep local documentation-build tests, strict clean documentation build, release QA tests and version consistency checks before publication.
- Remove the unconditional validation-only `workflow_dispatch` run from every release preflight. Admin verifies the current Linux CI definition before relying on this approach and reassesses relevant workflow/environment changes. Define concrete evidence and revalidation triggers with Admin and Release rather than assume that one successful run guarantees future versions.
- Keep the tag-triggered Linux validation and publication gates. Record the accepted trade-off: a Linux-only failure may first be detected after the tag exists. Preserve explicit push authorization, no publication on failed prerequisites, and escalation after partial or failed publication.
- Make release version, release-note heading and published documentation version metadata consistent. The current `docs/conf.py` release value is `0.1.0`, while the existing checker only validates tag syntax and the unique release-note heading. Specify and verify the authoritative version mechanism rather than introducing another independent version source.
- Resolve how committed preflight evidence relates to the tested commit and release tree: avoid an endless recheck loop caused only by recording results without allowing untested product, documentation, dependency or workflow changes to inherit earlier evidence.
- Update directly affected Requirements, Contract, examples, roles, checks and user documentation. Release is the mandatory consultee on release-gate/workflow changes; Admin owns workflow wiring.
- This Change does not publish a release, choose its version, push a branch/tag, introduce a package or executable distribution, or implement the separately discussed quality-finding severity/status enhancement.

### Observable Outcome

- The Contract and role/example surfaces agree on artifact ownership and provide an actionable source-release procedure.
- A release can complete its local preflight without a mandatory separate remote CI run for that version; Admin's actual Linux validation and its limits are recorded. Any required remote execution or branch push is explicitly authorized by the User before it happens.
- Tests reject inconsistent release/documentation versions and accept the intended matching case.
- The evidence-recording and tree-comparison rules admit a valid documented release without silently accepting unverified release-content changes.
- Existing tag-triggered strict Linux checks and publication ordering remain intact; tests and documentation builds pass.
